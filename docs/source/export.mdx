# Compiled Policies (lerobot-export)

A trained policy normally runs in PyTorch. PyTorch is flexible, but on a small robot computer it can be too slow, and a large policy may not fit in memory at all. `lerobot-export` solves this: it compiles a trained policy once, ahead of time, into a folder called a **bundle**. `lerobot-rollout` then runs the bundle in place of the checkpoint.

A bundle is useful because:

- **It is fast.** A compiler such as NVIDIA TensorRT tunes the policy's math for one chip.
- **It needs no PyTorch.** The robot process runs the compiled programs instead of the policy's Python code, and never imports PyTorch.
- **It is built for small boards.** Large policies such as π₀.₅ (pi0.5) and GR00T N1.7 are split into small programs, so they can be built and run on an NVIDIA Jetson Orin Nano with 8 GB of memory.
- **It checks itself.** The bundle carries a test frame. It is replayed at export and again before the robot moves.

```
             lerobot-export                  lerobot-rollout
checkpoint ─────────────────> bundle folder ──────────────────> robot
           (compile, check)                  (check, then run)
```

## Install

You need LeRobot, ExecuTorch 1.6 (the runtime that loads the compiled programs), and the compiler of the **backend** you choose. Install them on the machine that will run the policy.

| `--backend.type`      | Runs the policy on                                | Install                                                                           |
| --------------------- | ------------------------------------------------- | --------------------------------------------------------------------------------- |
| `executorch_tensorrt` | NVIDIA GPUs, including Jetson                     | `pip install "executorch>=1.6.0,<1.7.0" "torch-tensorrt[executorch]>=2.15,<2.16"` |
| `executorch_cuda`     | NVIDIA GPUs, including Jetson, without TensorRT   | `pip install "executorch>=1.6.0,<1.7.0"` (the CUDA build of ExecuTorch)           |
| `executorch_xnnpack`  | Arm and x86 CPUs                                  | `pip install "executorch>=1.6.0,<1.7.0"` (XNNPACK ships with ExecuTorch)          |
| `executorch_openvino` | Intel CPUs                                        | `pip install "executorch>=1.6.0,<1.7.0" openvino nncf`                            |
| `executorch_mlx`      | Apple Silicon Macs (GPU, through MLX)             | `pip install "executorch>=1.6.0,<1.7.0"` (the macOS wheel includes MLX)           |
| `executorch_coreml`   | Macs (CPU, GPU or Neural Engine, through Core ML) | `pip install "executorch>=1.6.0,<1.7.0"` (the macOS wheel includes Core ML)       |

- LeRobot has no `export` extra yet, so install these packages yourself.
- **Exporting needs PyTorch 2.15 or newer**, because ExecuTorch 1.6 and Torch-TensorRT 2.15 read only programs traced by PyTorch 2.15. This holds for every backend in the table. On Linux, LeRobot's own pins allow PyTorch 2.15, and the ExecuTorch 1.6 package pins `torch==2.15.0`, so install everything in one environment:

  ```bash
  pip install lerobot "executorch>=1.6.0,<1.7.0" "torch-tensorrt[executorch]>=2.15,<2.16"
  ```

  With an older PyTorch, `lerobot-export` stops before it starts and prints the install command for its backend.

- **ExecuTorch 1.6 needs fixes that are not in a release yet.** `executorch_cuda` and `executorch_tensorrt` need [pytorch/executorch#24324](https://github.com/pytorch/executorch/pull/24324), which names the weights file of each program. `executorch_openvino`, and every program that keeps an input check, need [pytorch/executorch#24298](https://github.com/pytorch/executorch/pull/24298). Both are changes to ExecuTorch 1.6 that are still in review, so use an ExecuTorch 1.6 release that has them.

- **Running a bundle never imports PyTorch.** `lerobot-rollout --bundle.path=<folder>` keeps that memory for the policy. PyTorch 2.15 is still installed, because ExecuTorch 1.6 depends on it, so run bundles from the export environment, or from one installed the same way.
- Torch-TensorRT must match your PyTorch version: Torch-TensorRT 2.15 works with PyTorch 2.15.
- `executorch_tensorrt` needs a Torch-TensorRT that has [pytorch/TensorRT#4953](https://github.com/pytorch/TensorRT/pull/4953), which is not in a release yet. Its `fallback_pytorch_plugin_ops` setting keeps an operation out of TensorRT when TensorRT would run it with a plugin that needs PyTorch, which a bundle does not load. `lerobot-export` refuses an older Torch-TensorRT.
- With a Torch-TensorRT that has [pytorch/TensorRT#4965](https://github.com/pytorch/TensorRT/pull/4965), `executorch_tensorrt` keeps one copy of each weight in host memory while TensorRT builds, instead of one for every layer that reads it transposed. An older Torch-TensorRT builds as before.
- A policy that starts from a random noise, such as pi0.5, SmolVLA or GR00T, draws that noise in a small program on the GPU. pytorch/TensorRT#4953 is also what lets `executorch_tensorrt` save that program.
- TensorRT builds an **engine** (its compiled form of the model) for one GPU model, and the engine runs only on that model. So export on the same kind of board that will run the policy.
- `executorch_tensorrt` runs any operation TensorRT cannot take on ExecuTorch's CUDA backend, so the whole program stays on the GPU. That backend compiles code at export, so for both `executorch_tensorrt` and `executorch_cuda` the export machine needs the CUDA compiler `nvcc` on its `PATH`. Like a TensorRT engine, the code `executorch_cuda` compiles is made for the GPU model that exports it.
- Without PyTorch, a program that ExecuTorch's CUDA backend compiled needs the system's OpenMP library, `libgomp.so.1`, which PyTorch otherwise brings. Ubuntu and JetPack have it (the `libgomp1` package), but a slim container image may not.
- On macOS, LeRobot pins an older PyTorch, for older macOS versions. So export and run from a second environment that overrides that pin, for example with [uv](https://docs.astral.sh/uv/), on a macOS version that PyTorch 2.15 supports:

  ```bash
  printf 'torch>=2.15,<2.16\ntorchvision>=0.29.2,<0.30\n' > torch-overrides.txt
  uv pip install --override torch-overrides.txt lerobot "executorch>=1.6.0,<1.7.0"
  ```

  The override replaces every PyTorch pin, also those of the packages after `lerobot`, so pin them to PyTorch 2.15 by hand, as above. torchvision is overridden too, because LeRobot pins it below the release that installs with PyTorch 2.15.

## Quick start with ACT

This example takes an [ACT](./act) policy trained for an SO-101 arm with one front camera.

### 1. Export

```bash
lerobot-export \
    --policy.path=outputs/train/act_so101/checkpoints/last/pretrained_model \
    --backend.type=executorch_tensorrt
```

The export runs in three steps, each in its own process:

1. It **traces** the policy: it runs the policy once and records every math operation into a graph.
2. It **compiles** that graph for the backend.
3. It **checks** the result against PyTorch.

The last lines look like this:

```
INFO ... Tracing model
INFO ... Compiling model with executorch_tensorrt
INFO ... Checking the bundle
INFO ... Bundle test case: largest difference 5.40e-06 (tolerance 2e-05)
INFO ... Wrote outputs/export/act_executorch_tensorrt
```

The bundle is a plain folder:

```
outputs/export/act_executorch_tensorrt/
  export.json         the manifest: which programs to run, and how
  model.pte           the compiled program
  test.safetensors    a test frame and the actions PyTorch computed for it
  policy_config.json  the policy's config, kept as a record
```

A program can also have a second file beside it, its data file. It holds the weights of the program's part that runs on ExecuTorch's CUDA backend.

### 2. Check the bundle (optional)

If you exported on another machine, check the bundle on the robot computer first. This loads the programs and replays the test frame. It does not touch the robot:

```bash
lerobot-check-bundle outputs/export/act_executorch_tensorrt
```

### 3. Run it on the robot

Pass the bundle folder as `--bundle.path` in place of `--policy.path`. The robot options are the same as for a checkpoint:

```bash
lerobot-rollout \
    --bundle.path=outputs/export/act_executorch_tensorrt \
    --robot.type=so101_follower \
    --robot.port=/dev/ttyACM0 \
    --robot.cameras="{ front: {type: opencv, index_or_path: 0, width: 640, height: 480, fps: 30}}" \
    --duration=30
```

Before the robot connects, `lerobot-rollout` loads the programs, replays the test frame, and checks that the robot matches what the bundle takes:

```
INFO ... Loading the bundle from 'outputs/export/act_executorch_tensorrt'...
INFO ... Bundle test case: largest difference 5.40e-06 (tolerance 2e-05)
INFO ... Bundle loaded from outputs/export/act_executorch_tensorrt (backend executorch_tensorrt)
```

Then the robot moves, as with any policy. While it runs, an action that is NaN or infinite stops the run before it reaches the motors. After Ctrl-C or `--duration`, the robot returns to where it started (turn this off with `--return_to_initial_position=false`) and disconnects. After an error it is not moved again.

`lerobot-rollout --bundle.path=<folder> --help` lists its options: `--bundle.path`, `--robot.*`, `--fps`, `--duration`, `--interpolation_multiplier`, `--task`, `--rename_map`, `--return_to_initial_position`, and `--config_path` for a file that holds them. Give `--bundle.path` on the command line even then, because in the file alone it does not select this mode. It runs the base strategy only, because it imports no PyTorch. Every `--strategy.*` option, recording (`--dataset.*`), teleoperation (`--teleop.*`), `--inference.*`, `--planner`, `--interactive` and `--display_data` need PyTorch, so they are refused, and so are `--policy.*`, `--device` and `--use_torch_compile`, since a bundle runs exactly as it was compiled. Of the installed plugins, cameras load, a robot plugin only when `--robot.type` names a robot no loaded package has (or a `--config_path` file names the robot), and a runtime only when the bundle names one LeRobot does not have, because any plugin may import PyTorch. `--robot.discover_packages_path` imports the package of a robot plugin, which registers the robot, so then no installed robot plugin loads. Unlike in `lerobot-rollout`, the package's other modules are not loaded, because they may import PyTorch. The Unitree G1 is not available in this mode, because its config needs PyTorch.

### Options

| Flag                          | What it does                                                                                                                        |
| ----------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `--policy.path`               | The checkpoint: a local folder or a Hub repository. `--policy.pretrained_revision` picks a Hub revision.                            |
| `--backend.type`              | The compiler, from the table above.                                                                                                 |
| `--output_dir`                | Where to write the bundle. Defaults to `outputs/export/<policy type>_<backend type>`. The folder must not exist yet.                |
| `--task`                      | The task, for a policy that reads one, such as SmolVLA or pi0.5. See [Tasks](#tasks).                                               |
| `--dataset.repo_id`           | The dataset the policy was trained on. The export takes the robot's frame and the tasks from it. See [Tasks](#tasks).               |
| `--tolerance`                 | The largest difference allowed between compiled and PyTorch actions. See [Built-in checks](#built-in-checks).                       |
| `--max_task_tokens`           | For a bundle that runs any task: the longest task prompt, in tokens. See [Tasks](#tasks).                                           |
| `--seed`                      | Seeds the random test frame. Defaults to `1000`.                                                                                    |
| `--backend.workspace_size`    | TensorRT only: the most GPU memory, in bytes, that TensorRT may use as scratch while it builds.                                     |
| `--backend.compute_units`     | Core ML only: the hardware Core ML may use, `all` (the default), `cpu_only`, `cpu_and_gpu` or `cpu_and_ne` (CPU and Neural Engine). |
| `--backend.compute_precision` | Core ML only: `float32` (the default) or `float16`. The Neural Engine runs only `float16`.                                          |

With the default recipe, a checkpoint trained with a PEFT adapter (a small set of extra weights, such as LoRA) is exported with the adapter merged into the base weights.

A bundle on the Hub must be downloaded first, for example with `hf download <repo> --local-dir <folder>`. A bundle passed to `lerobot-rollout` as `--policy.path` is refused with a pointer to `--bundle.path`.

Run only bundles you trust, as you would any program. A bundle's programs are compiled code (a program for a GPU can carry a native library that loads with it), and its manifest names Python modules to import. `lerobot-check-bundle` and `lerobot-rollout` never load modules from the folder they start in, but a Python command such as `python -m lerobot.bundle` does, so start such a command only from outside a downloaded bundle's folder.

## How it works

### Recipe and backend

Two pieces do the work, and each one knows only one thing:

- A **recipe** knows the policy. It cuts the policy into one or more **parts**, gives example inputs for each, and makes the test case.
- A **backend** knows the compiler. It turns one traced part into one program file, for example an ExecuTorch `.pte` file that runs on TensorRT.

```
EXPORT                                                          RUN
checkpoint -> recipe -> parts -> backend -> bundle folder -> runtime -> lerobot-rollout
              knows the policy    knows the compiler           loads the program files
```

So any recipe can be paired with any backend. Whether a given policy compiles still depends on the compiler: see [Supported policies and backends](#supported-policies-and-backends).

### One recipe per policy

`lerobot-export` uses the policy's own recipe when it has one. Otherwise it uses the **default recipe**. The default recipe makes a single program that does everything `lerobot-rollout` does for one chunk of actions: it converts the camera images, runs the saved preprocessor, runs the policy, and runs the saved postprocessor. The program returns actions in robot units.

The default recipe fits a policy that:

- predicts a chunk of actions from the current frame only,
- draws at most one random starting noise, and
- gives the same chunk twice for the same frame and noise.

For any other policy, it stops with the reason. For example, ACT with temporal ensembling (which mixes several past chunks) cannot be exported this way.

### The bundle is the contract

The bundle holds everything `lerobot-rollout` needs, and nothing else. The robot runs the compiled programs, not the policy's Python code. Here is the manifest of the ACT bundle above. Your values, such as `action_scale`, will differ:

```json
{
  "format_version": 1,
  "backend": "executorch_tensorrt",
  "runtime": "executorch",
  "runtime_imports": ["torch_tensorrt_executorch_runtime"],
  "programs": {
    "model": { "file": "model.pte", "data": null }
  },
  "runs": [
    {
      "name": "model",
      "program": "model",
      "inputs": ["observation.images.front", "observation.state"],
      "outputs": ["action"]
    }
  ],
  "constants": null,
  "task_tokens": null,
  "noise_shape": null,
  "history": {},
  "carry": {},
  "task": null,
  "action_names": null,
  "action_scale": [20.0, 20.0, 20.0, 20.0, 20.0, 20.0],
  "tolerance": 2e-5,
  "target": {
    "device": "cuda",
    "gpu": "NVIDIA H100",
    "compute_capability": "9.0"
  },
  "runtime_versions": {
    "executorch": "1.6.0",
    "tensorrt": "11.4.0.106",
    "torch_tensorrt_executorch_runtime": "2.15.0"
  },
  "test_case": "test.safetensors"
}
```

- `programs` lists each compiled program file once, by name, with the data file the runtime loads beside it, if any.
- `runs` run in order, each naming its program, so one program can run several times. They pass values to each other **by name**. An input can be a key of the robot's frame (such as `observation.state`), `noise`, a named constant, or an output of an earlier run. The last run outputs `action`.
- On a GPU backend, the first run takes no inputs and draws `noise` on the GPU, so a chunk copies only the robot's frame there. ExecuTorch 1.6 cannot seed that draw, so it cannot be replayed exactly. Replays and debugging use noise from the host, through the same `noise` input, as the built-in check does.
- `runtime_imports` are Python modules to import before the programs load, such as the one that adds TensorRT to ExecuTorch.
- `action_scale` is the spread of each action in the training data, in robot units. The checks use it.
- `target` is the GPU the programs were built on, when they run only on that kind of GPU, as a TensorRT engine does. `runtime_versions` are the versions of the Python modules the programs need to load.

A version of LeRobot refuses a bundle whose format or keys it does not know, and says whether to upgrade LeRobot or to export again.

### Built-in checks

The export makes a random test frame and records the actions PyTorch computes for it. Then:

- **At export**, the finished bundle replays the test frame in a fresh process, the same way `lerobot-rollout` will. If the actions differ too much from PyTorch's, nothing is written.
- **At load**, `lerobot-rollout` replays the test frame again, before the robot connects. It also checks the robot's cameras and state (after `--rename_map`), the number of joints, and the joint names when the policy recorded them. Before any program loads, a bundle is refused if this machine does not have its GPU or its runtime modules (another version of a module only gets a warning), or if its programs read a value that nothing gives. While the robot runs, every chunk must have the right shape and be finite before it is used.

The difference is measured in **normalized units**: each action's difference is divided by its `action_scale`. So the same tolerance means the same thing on every robot. The default tolerance is 2e-05 for a policy with float32 (32-bit) weights: the compiled program computes in full float32, as PyTorch does. For one with bfloat16 (16-bit) weights it is 0.075, because a compiler may sum 16-bit numbers in another order. In bfloat16, a recipe whose policy runs ten denoising steps, such as pi0.5's, uses 0.2: the steps amplify rounding, as measured on pi0.5's test frame. That catches only large errors: a recipe that swapped two cameras would move pi0.5's actions by about 0.03 there, so check a change to a recipe in float32, where the tolerance is 2e-05. Change the tolerance with `--tolerance`.

<Tip>

float32 is the default because it matches PyTorch most closely. A big policy, such as pi0, pi0.5 or GR00T, exports faster and runs faster in bfloat16. Add `--policy.dtype=bfloat16` to `lerobot-export`, and the check then uses the bfloat16 tolerance.

</Tip>

### Big models: bundles with several programs

On an 8 GB board, pi0.5, GR00T N1.7 and SmolVLA do not fit well as one program. So their recipes cut one chunk into a **chain** of small programs. The programs run in the order the manifest lists their runs, pass values to each other by name, and keep those values in GPU memory. pi0.5 starts from random noise and removes it in ten steps, and its chain looks like this:

```
embed                 cameras, state, task          -> the prompt, as vectors
language_model_0..k   a few language model layers   -> what those layers remember about the prompt
step (x10)            that memory, noisy actions    -> less noisy actions
actions               clean actions                 -> actions in robot units
```

The `step` is one program file that runs ten times, each time with a different time value from a `constants.safetensors` file. The file loads once.

Two things let a board with 8 GB build such a policy:

- The recipe loads only the weights of the part it is tracing, then frees them.
- Each part is compiled in a process of its own, and the memory goes back to the system when that process ends.

The pi0.5 and GR00T recipes read each part's weights from the checkpoint's `model.safetensors`, so they refuse a checkpoint that holds only a PEFT adapter. Merge the adapter into its base policy first, then export the merged folder:

```python
from lerobot.configs.policies import PreTrainedConfig
from lerobot.policies.factory import load_pretrained_policy, make_pre_post_processors

adapter, merged = "path/to/adapter", "path/to/merged"
config = PreTrainedConfig.from_pretrained(adapter)
load_pretrained_policy(config).merge_and_unload().save_pretrained(merged)
for processor in make_pre_post_processors(config, pretrained_path=adapter):
    processor.save_pretrained(merged)
```

The export also compares the chain's actions with the whole policy's own, which needs twice the policy's weights in memory. On a board that does not have that memory, such as an 8 GB board for pi0.5, the export skips that comparison and logs a line saying so. The bundle is then still compared with PyTorch running the same parts, but not with the whole policy.

### Actions written as tokens

pi0-FAST does not compute numbers for its actions. It writes each action chunk as text: `Action: `, then **FAST tokens** (a compressed form of the chunk), then `|`. It writes one token at a time, and each token needs a full pass of its language model. Its recipe makes this chain:

```
prefill (x1)     cameras, state       -> the first token, and the model's memory of the prompt
step (x255)      the tokens so far    -> the next token
(decoding)       the tokens           -> normalized actions, in NumPy
actions          normalized actions   -> actions in robot units
```

A program cannot stop early, so the bundle runs every step up to `max_decoding_steps` (256 by default), and the decoding ignores the tokens after `|`, as the policy does. A chunk therefore takes as long as the longest answer. For a checkpoint whose answers are short, a smaller `--policy.max_decoding_steps` at export makes each chunk faster, and cuts longer answers as the PyTorch policy with that setting would. Turning the tokens back into numbers is not a program: the bundle does it with NumPy and the FAST tokenizer file it carries, so it needs no PyTorch either. pi0-FAST writes the robot's state into its prompt as text, so its bundle runs only the task given at export.

The recipe exports greedy decoding with the KV cache, which is how pi0-FAST decodes by default (`--policy.temperature=0` and `--policy.use_kv_cache=true`), in float32. A checkpoint saved in bfloat16 needs `--policy.dtype=float32`: in bfloat16 the exported steps round differently from the policy and soon pick other tokens. Before it compiles anything, it checks that the chain generates exactly the policy's tokens for two frames, and that the NumPy decoding gives the policy's actions.

The export's test frames are random images. A fine-tuned checkpoint can answer them with text that does not start with `Action:`, and a checkpoint with `validate_action_token_prefix` on (the default) then refuses its own answer, as it would on the robot. Export such a checkpoint with `--policy.validate_action_token_prefix=false`.

### Past frames

Diffusion Policy, Multi-Task DiT and VQ-BeT read the last few frames, not only the current one. In PyTorch the policy keeps them in queues that fill on every control tick. A compiled program keeps nothing between runs, so the bundle names those frames in its manifest under `history`, with how many to keep. `lerobot-rollout` then keeps them on every tick and passes them to the programs, oldest first. A policy that samples random numbers inside its steps reads them from the bundle's `noise`, so the compiled policy samples like the PyTorch one.

Diffusion Policy and Multi-Task DiT run their encoder once per chunk, and one denoising step many times in a loop, the same way the pi0.5 chain runs its `step`.

### Values kept between chunks

Some policies keep a value from one chunk to the next, such as a planner that starts each plan from where its previous one ended. A compiled program keeps nothing between runs, so such a program takes the value as an input and returns the new one. The bundle names these values in its manifest under `carry`, with their shapes. `lerobot-rollout` passes each one from a chunk to the next, and starts it again from zeros after a reset. The test case of such a bundle holds a few chunks, and the check plays them in order, so it also checks what is passed on.

TD-MPC is such a planner. It plans each chunk by refining a guess over a few rounds, and starts that guess from where its previous plan ended, or from zeros after a reset. Its random numbers come from the bundle's `noise`, like those of the policies above.

Some policies also compute their first chunks after a reset in another way, such as one that builds a cache from its first frames. Their bundle lists the runs of those chunks under `first_runs`, one list per chunk, and later chunks run `runs`. A value that the first chunk writes, in its own type and on its own device, is listed under `carry` without a shape, so it never starts from zeros. The test case of such a bundle plays a few chunks from a reset tick by tick, as a robot would, and holds the action played at each tick, so the check covers every chunk.

### Tasks

A vision-language-action policy reads a task such as "pick up the cube". To read it, the policy first splits the text into **tokens** (word pieces) with its **tokenizer**, and looks up a vector for each token in its **embedding table**. A compiled program cannot run a tokenizer, so a bundle handles the task in one of two ways:

- **Fixed task.** The default recipe stores the task inside the program. Give it with `--task="pick up the cube"`, or let the export take the first task of `--dataset.repo_id`. The bundle then runs only that task.
- **Any task.** The pi0.5 and GR00T recipes write `task_tokens` into the bundle: the policy's tokenizer file and its embedding table. At run time, the bundle turns any task into vectors without PyTorch. Tasks known at export, such as the dataset's, are stored ready to use. A new task is tokenized once, in a short-lived child process, so the tokenizer's memory does not stay in the robot process. This needs the `tokenizers` package on the robot computer: `pip install "tokenizers>=0.22"`.

For an any-task bundle, the task's prompt must fit in `--max_task_tokens`. The prompt is the task plus a few fixed words the policy adds around it. By default, the budget is a little more than the longest prompt known at export.

Change the task with `--task` when you start `lerobot-rollout --bundle.path=<folder>`.

### PyTorch at export and at run time

- The `lerobot-export` command itself never imports PyTorch. The PyTorch work happens in the trace and compile processes, which give their memory back when they end.
- `lerobot-rollout --bundle.path=<folder>` loads the compiled programs and never imports PyTorch. Of the installed plugins it loads cameras, and a robot or runtime plugin only when the command or the bundle names a robot or runtime no loaded package has, since a plugin may import PyTorch.

## Run pi0.5 and GR00T on a Jetson Orin Nano

The Jetson Orin Nano has 8 GB of memory, shared by the CPU and the GPU. The pi0.5 and GR00T recipes are made for it: they build one small part at a time. Both fit and run on a Jetson Orin Nano 8 GB, with the numbers below.

### 1. Prepare the board

- Use JetPack 7, NVIDIA's software for Jetson boards. It brings CUDA 13.
- Install LeRobot and the `executorch_tensorrt` packages from [Install](#install). Jetson boards are aarch64 (64-bit Arm), so use the aarch64 builds for CUDA 13.
- Put the CUDA compiler on your `PATH`: `export PATH=/usr/local/cuda/bin:$PATH`.
- Turn on swap. During a TensorRT build, memory the CPU uses can move to swap, but memory given to the GPU cannot.

### 2. Export on the board

Export on the Orin Nano itself, because a TensorRT engine runs only on the GPU model that built it. The first export takes roughly 10 to 15 minutes.

```bash
lerobot-export \
    --policy.path=<user>/<pi05_checkpoint> \
    --policy.dtype=bfloat16 \
    --backend.type=executorch_tensorrt \
    --dataset.repo_id=<user>/<dataset> \
    --task="pick up the cube"
```

For GR00T N1.7, pass a GR00T checkpoint instead. Close other programs while it runs: the export uses most of the board's memory at its peak.

### 3. Run

```bash
lerobot-rollout \
    --bundle.path=outputs/export/pi05_executorch_tensorrt \
    --robot.type=so101_follower \
    --robot.port=/dev/ttyACM0 \
    --robot.cameras="{ front: {type: opencv, index_or_path: 0, width: 640, height: 480, fps: 30}}" \
    --task="put the cube in the box" \
    --duration=60
```

Use the camera names and sizes the policy was trained with. The task can be any task whose prompt fits in the bundle's token budget.

LingBot-VLA v2 also passed the **Program** test with TensorRT, but only with `--policy.precompute_grid_thw=true`. It makes its vision model compute the layout of image patches once, instead of on every call, so it assumes that the camera layout does not change while the robot runs.

Other policies have not been tested with `lerobot-export`.

## Troubleshooting

**`outputs/export/... already exists. Pick another --output_dir.`**
The export never overwrites a bundle. Delete the old folder, or pass `--output_dir`.

**`The executorch_tensorrt backend needs PyTorch 2.15 or newer to export, but PyTorch 2.11.0 is installed.`**
This environment has an older PyTorch. Install PyTorch 2.15 as the message shows: in the same environment on Linux, or in a second environment on macOS (see [Install](#install)).

**`The executorch_tensorrt backend needs: pip install ...`**, or at run time, **`This bundle needs the Python module 'torch_tensorrt_executorch_runtime' to load its programs.`**
The backend's packages are missing on this machine. Install them as shown in [Install](#install).

**`The exported policy does not reproduce its test case (... > 2e-05). Export it again on this device.`**
The compiled actions differ from PyTorch's by more than the tolerance. With TensorRT, this usually means the bundle was built on another GPU model: export on the board that runs it. Raise `--tolerance` only if you know the difference does not matter for your task.

**`The robot does not match the exported policy, which takes observation.images.front (480, 640, 3) (the robot gives None).`**
The robot's cameras or joints differ from the ones the policy was trained with. Give the cameras the same names and sizes, or map the names with `--rename_map`, for example `--rename_map='{"observation.images.wrist": "observation.images.front"}'`.

**`This exported policy runs only the task it was exported for, ...`** or **`The task ... is 40 tokens long, but this exported policy takes at most 32.`**
A fixed-task bundle runs only its task: export again with the new `--task`. An any-task bundle has a token budget: shorten the task, or export again with a larger `--max_task_tokens`.

**`This act checkpoint cannot be exported: ...`**
The default recipe does not fit this policy, and the message says why. Change the setting it names if your policy works without it, or write a recipe for the policy (see below).

## Add a recipe or a backend

### A recipe

A recipe lives beside the policy's configuration, in `src/lerobot/policies/<type>/export_<type>.py`. Its class name is the policy's config class name with `ExportRecipe` in place of `Config`: `PI05Config` gets `PI05ExportRecipe`. `lerobot-export` finds it on its own.

```python
from collections.abc import Iterator

from lerobot.export.recipe import ExportRecipe, Part, TestCase


class MyPolicyExportRecipe(ExportRecipe):
    def parts(self) -> Iterator[Part]:
        # Yield the parts in the order they run. Each one is traced, saved and freed before the next;
        # the parts are compiled afterwards, each in a process of its own.
        yield Part(
            name="model",
            module=MyChunkModule(self.policy, self.preprocessor, self.postprocessor),
            example_inputs=(image, state),
            inputs=["observation.images.front", "observation.state"],
            outputs=["action"],
        )

    def test_case(self) -> TestCase:
        # A frame as the robot sends it, and the actions PyTorch computes for it.
        return TestCase(frame=frame, noise=None, actions=actions, action_scale=action_scale)
```

Two optional methods cover bigger policies:

- `load` (a class method) builds the recipe from the export configuration. Override it to load each part's weights only when that part is traced.
- `plan()` returns a `RunPlan`, which can hold:
  - `runs`: the list of runs (`ProgramRun`, each naming the part it runs as its program), for a part that runs more than once. Record them in `parts()` as you yield the parts, so the two cannot disagree;
  - `constants`: named arrays the runs read, such as time values;
  - `task_tokens`: a `TaskTokenData`, for a bundle that runs any task;
  - `history`: how many past frames of each frame key the programs read;
  - `carry`: the values the runs pass from one chunk to the next, with their shapes.

`tests/export/chain_recipe.py` is a small working example of a chain with a repeated part and constants. `policies/pi05/export_pi05.py`, `policies/groot/export_groot.py` and `policies/smolvla/export_smolvla.py` are full ones. `policies/diffusion/export_diffusion.py` shows a recipe that reads past frames, `policies/tdmpc/export_tdmpc.py` one that carries a value between chunks, and `policies/gaussian_actor/export_gaussian_actor.py` a small change to the default recipe.

### A backend

A backend is one config class, registered under its `--backend.type` name. It compiles one part, already traced by `torch.export`, into one program file. An installed package named `lerobot_backend_<name>` adds a backend when imported, the way `lerobot_runtime_<name>` adds a runtime (below). A backend whose programs ExecuTorch loads builds on `ExecuTorchConfig`, which sets the runtime, the file suffix and the PyTorch the compiler needs:

```python
from dataclasses import dataclass
from pathlib import Path

from torch.export import ExportedProgram

from lerobot.export.backends.executorch import EXECUTORCH, ExecuTorchConfig
from lerobot.export.configs import ExportBackendConfig


@ExportBackendConfig.register_subclass("executorch_mychip")
@dataclass
class ExecuTorchMyChipConfig(ExecuTorchConfig):
    device = "cpu"  # where the programs run; the parts are traced and compiled there too
    runtime_imports = ("mychip_executorch",)  # modules that register the chip with the runtime, if any
    runtime_modules = ("executorch", "mychip_executorch")  # modules whose versions the bundle records
    packages = (EXECUTORCH, "mychip-executorch")  # what to install beside LeRobot to export

    def compile(self, program: ExportedProgram, path: Path) -> Path | None:
        from executorch.exir import to_edge_transform_and_lower
        from mychip_executorch import MyChipPartitioner

        edge = to_edge_transform_and_lower(program, partitioner=[MyChipPartitioner()])
        path.write_bytes(edge.to_executorch().buffer)
        return None  # or a data file written beside `path`, such as separate weights
```

A backend whose `device` is `cuda` records the GPU it builds on in the bundle's `target`, since its programs then run only on that kind of GPU. LeRobot's own backends live in `src/lerobot/export/backends/`.

A backend with a new file format, such as ONNX, also needs a **runtime**: a class that loads one program file and runs it on NumPy arrays (see `Program` in `lerobot.bundle.runtime`). An installed package named `lerobot_runtime_<name>` adds it when imported:

```python
from lerobot.bundle.runtime import Runtime, register_runtime

register_runtime("onnxruntime", Runtime(load=OnnxProgram))
```

`lerobot-rollout --bundle.path=<folder>` imports such packages only when a bundle names a runtime LeRobot does not have. Nothing in LeRobot changes, and a runtime must not import PyTorch.
