# Compiled Policies (lerobot-export)

A trained policy normally runs in PyTorch. PyTorch is flexible, but on a small robot computer it can be too slow, and a large policy may not fit in memory at all. `lerobot-export` solves this: it compiles a trained policy once, ahead of time, into a folder called a **bundle**.

A bundle is useful because:

- **It is fast.** A compiler such as NVIDIA TensorRT tunes the policy's math for one chip.
- **It does not load PyTorch.** The robot process runs the compiled programs instead of the policy's Python code, and never imports PyTorch, so that memory stays free for the policy.
- **It is built for small boards.** Large policies such as π₀ (pi0), π₀.₅ (pi0.5) and GR00T N1.7 are split into small programs, so they can be built and run on an NVIDIA Jetson Orin Nano with 8 GB of memory.
- **It checks itself.** The bundle carries a test frame. It is replayed at export and again by `lerobot-check-bundle`.

```
             lerobot-export
checkpoint ─────────────────> bundle folder
           (compile, check)
```

## Install

You need LeRobot, ExecuTorch 1.6 (the runtime that loads the compiled programs), and the compiler of the **backend** you choose. Install them on the machine that will run the policy.

| `--backend.type`      | Runs the policy on                                              | Install                                                                  |
| --------------------- | --------------------------------------------------------------- | ------------------------------------------------------------------------ |
| `executorch_xnnpack`  | Arm and x86 CPUs                                                | `pip install lerobot 'executorch>=1.6.0,<1.7.0'`                         |
| `executorch_openvino` | Intel CPUs                                                      | `pip install lerobot 'executorch>=1.6.0,<1.7.0' openvino nncf`           |
| `executorch_mlx`      | Apple Silicon Macs (GPU, through MLX)                           | `pip install lerobot 'executorch>=1.6.0,<1.7.0'`                         |
| `executorch_coreml`   | Apple Silicon Macs (CPU, GPU or Neural Engine, through Core ML) | `pip install lerobot 'executorch>=1.6.0,<1.7.0'` on Python 3.13 or older |
| `executorch_cuda`     | NVIDIA GPUs, including Jetson, without TensorRT                 | `pip install lerobot 'executorch>=1.6.0,<1.7.0'` on Linux                |
| `executorch_tensorrt` | NVIDIA GPUs, including Jetson                                   | `pip install lerobot` and `torch_tensorrt[executorch]` on Linux          |

- The NVIDIA backends export on the GPU and load the policy straight onto it, and transformers then needs `accelerate` to load the models a policy builds from a checkpoint, such as its vision or text encoder, so install `accelerate` with them.
- **Exporting needs PyTorch 2.15 or newer**, because ExecuTorch 1.6 and Torch-TensorRT 2.15 read only programs traced by PyTorch 2.15. This holds for every backend in the table. LeRobot's own pins allow PyTorch 2.15, and the ExecuTorch 1.6 package pins `torch==2.15.0`, so each command above installs everything in one environment.
- On Linux, ExecuTorch's wheel on PyPI is its CUDA 13.2 build, for the same CUDA as the PyTorch 2.15 on PyPI, so `executorch_cuda` needs nothing more. The same wheel imports and runs the CPU backends on a machine without an NVIDIA driver. For `executorch_tensorrt`, add Torch-TensorRT:

  ```bash
  pip install lerobot 'torch_tensorrt[executorch]'
  ```

  Torch-TensorRT's `executorch` extra brings ExecuTorch and `torch-tensorrt-executorch-runtime`, which loads the TensorRT engines of a bundle without PyTorch, so do not install them separately. It must match your PyTorch version: Torch-TensorRT 2.15 works with PyTorch 2.15.

- With an older PyTorch, `lerobot-export` stops before it starts and prints the install command for its backend.
- **ExecuTorch 1.6 has fixes these backends need.** `executorch_cuda` and `executorch_tensorrt` need [pytorch/executorch#24489](https://github.com/pytorch/executorch/pull/24489), which names the weights file of each program. `executorch_openvino`, and every program that keeps an input check, need [pytorch/executorch#24298](https://github.com/pytorch/executorch/pull/24298).
- **Running a bundle never imports PyTorch.** PyTorch 2.15 is still installed, because ExecuTorch 1.6 depends on it, so run bundles from the export environment, or from one installed the same way.
- `executorch_tensorrt` needs a Torch-TensorRT that has [pytorch/TensorRT#4953](https://github.com/pytorch/TensorRT/pull/4953), such as Torch-TensorRT 2.15. Its `fallback_pytorch_plugin_ops` setting keeps an operation out of TensorRT when TensorRT would run it with a plugin that needs PyTorch, which a bundle does not load.
- `executorch_tensorrt` keeps one copy of each weight in host memory while TensorRT builds, instead of one for every layer that reads it transposed, with Torch-TensorRT's `deduplicate_weights` setting from [pytorch/TensorRT#4965](https://github.com/pytorch/TensorRT/pull/4965).
- On a CUDA device, a policy that starts from a random noise, such as pi0.5, SmolVLA or GR00T, draws that noise in a small program on the GPU. pytorch/TensorRT#4953 is also what lets `executorch_tensorrt` save that program.
- TensorRT builds an **engine** (its compiled form of the model) for one GPU model, and the engine runs only on that model. So export on the same kind of board that will run the policy.
- `executorch_tensorrt` runs any operation TensorRT cannot take on ExecuTorch's CUDA backend, so the whole program stays on the GPU. That backend compiles code at export, so for both `executorch_tensorrt` and `executorch_cuda` the export machine needs the CUDA compiler `nvcc`. JetPack and the CUDA toolkit have it in `/usr/local/cuda/bin`. Without them, install it from PyPI and point `CUDA_HOME` at it:

  ```bash
  pip install 'cuda-toolkit[nvcc]==13.2.*'
  export CUDA_HOME=$(python -c "import os, nvidia; print(os.path.join(list(nvidia.__path__)[0], 'cu13'))")
  export PATH=$CUDA_HOME/bin:$PATH
  ```

  Like a TensorRT engine, the code `executorch_cuda` compiles is made for the GPU model that exports it.

- Without PyTorch, a program that ExecuTorch's CUDA backend compiled needs the system's OpenMP library, `libgomp.so.1`, which PyTorch otherwise brings. Ubuntu and JetPack have it (the `libgomp1` package), but a slim container image may not.

## Quick start with ACT

This example takes an [ACT](./act) policy trained for an SO-101 arm with one front camera.

### 1. Export

```bash
lerobot-export \
    --policy.path=outputs/train/act_so101/checkpoints/last/pretrained_model \
    --backend.type=executorch_tensorrt
```

The export runs in three steps, in separate processes:

1. It **traces** the policy: it runs the policy once and records every math operation into a graph.
2. It **compiles** that graph for the backend.
3. It **checks** the result against PyTorch.

It logs each step as it starts and how long it took:

```
INFO ... Tracing model
INFO ... Traced the policy in 19 s
INFO ... [1/2] Compiling model with executorch_tensorrt
INFO ... [1/2] Compiling model with executorch_tensorrt: done in 37 s
INFO ... [2/2] Checking the bundle
INFO ... Bundle test case: largest difference 5.56e-07 (tolerance 2e-05)
INFO ... [2/2] Checking the bundle: done in 3 s
INFO ... Wrote outputs/export/act_executorch_tensorrt in 59 s
```

A step that runs longer than a minute says so every minute, such as `[1/2] Compiling model with executorch_cuda: still running after 60 s`, so the export of a large policy is never silent.

The compiler's own logs, such as a line for each operator TensorRT converts, are left out, except its warnings. `--log_level=DEBUG` shows them, with the logs of ExecuTorch and of PyTorch (torch.export, and Inductor for `executorch_cuda`). For PyTorch's own debug logs, also set `TORCH_LOGS`, for example `TORCH_LOGS="+export"` (see [PyTorch logging](https://docs.pytorch.org/docs/stable/logging.html)).

The bundle is a plain folder:

```
outputs/export/act_executorch_tensorrt/
  export.json         the manifest: which programs to run, and how
  model.pte           the compiled program
  test.safetensors    a test frame and the actions PyTorch computed for it
  policy_config.json  the policy's config, kept as a record
```

A program can also have a second file beside it, its data file. It holds the weights of the program's part that runs on ExecuTorch's CUDA backend.

### 2. Check the bundle

If you exported on another machine, check the bundle on the robot computer. This loads the programs and replays the test frame. It does not touch the robot:

```bash
lerobot-check-bundle outputs/export/act_executorch_tensorrt
```

With the default recipe, a checkpoint trained with a PEFT adapter (a small set of extra weights, such as LoRA) is exported with the adapter merged into the base weights.

A bundle on the Hub must be downloaded first, for example with `hf download <repo> --local-dir <folder>`.

Run only bundles you trust, as you would any program. A bundle's programs are compiled code (a program for a GPU can carry a native library that loads with it), and its manifest names Python modules to import. `lerobot-check-bundle` never loads modules from the folder it starts in, but a Python command such as `python -m lerobot.bundle` does, so start such a command only from outside a downloaded bundle's folder.

## How it works

### Recipe and backend

Two pieces do the work, and each one knows only one thing:

- A **recipe** knows the policy. It cuts the policy into one or more **parts**, gives example inputs for each, and makes the test case.
- A **backend** knows the compiler. It turns one traced part into one program file, for example an ExecuTorch `.pte` file that runs on TensorRT.

```
EXPORT                                                          RUN
checkpoint -> recipe -> parts -> backend -> bundle folder -> runtime
              knows the policy    knows the compiler           loads the program files
```

So any recipe can be paired with any backend. Whether a given policy compiles still depends on the compiler: see [Supported policies and backends](#supported-policies-and-backends).

### One recipe per policy

`lerobot-export` uses the policy's own recipe when it has one. Otherwise it uses the **default recipe**. The default recipe makes a single program that does everything `lerobot-rollout` does for one chunk of actions: it converts the camera images, runs the saved preprocessor, runs the policy, and runs the saved postprocessor. The program returns actions in robot units.

The default recipe fits a policy that:

- predicts a chunk of actions from the current frame only,
- draws at most one random starting noise,
- computes the same chunk when it is given the standard normal draw behind that noise instead of drawing it, and
- gives the same chunk twice for the same frame and noise.

For any other policy, it stops with the reason. For example, ACT with temporal ensembling (which mixes several past chunks) cannot be exported this way.

A program takes every image as 8-bit, so its bundle cannot run a policy that reads a depth camera. Only the dataset marks which cameras are depth maps, so the export refuses such a policy only when you give its dataset with `--dataset.repo_id`. Give it whenever the policy reads a one-channel camera: LeRobot records every one-channel robot camera as a depth map.

### The bundle is the contract

The bundle holds everything needed to run the policy, and nothing else. The robot runs the compiled programs, not the policy's Python code. Here is the manifest of the ACT bundle above. Your values, such as `action_scale`, will differ:

```json
{
  "format_version": 1,
  "backend": "executorch_tensorrt",
  "runtime": "executorch",
  "runtime_imports": ["torch_tensorrt_executorch_runtime"],
  "runtime_options": {
    "TensorRTBackend": { "use_shared_activation_scratch": true }
  },
  "programs": {
    "model": { "file": "model.pte", "data": null }
  },
  "runs": [
    {
      "name": "model",
      "program": "model",
      "inputs": ["observation.images.front", "observation.state"],
      "outputs": ["action"]
    }
  ],
  "first_runs": [],
  "constants": null,
  "task_tokens": null,
  "action_tokens": null,
  "noise_shape": null,
  "history": {},
  "carry": {},
  "task": null,
  "action_names": null,
  "action_scale": [20.0, 20.0, 20.0, 20.0, 20.0, 20.0],
  "tolerance": 2e-5,
  "target": {
    "device": "cuda",
    "gpu": "NVIDIA H100",
    "compute_capability": "9.0"
  },
  "runtime_versions": {
    "executorch": "1.6.0",
    "tensorrt": "11.4.0.106",
    "torch_tensorrt_executorch_runtime": "0.2.1"
  },
  "exact_runtime_modules": ["tensorrt"],
  "test_case": "test.safetensors"
}
```

- `programs` lists each compiled program file once, by name, with the data file the runtime loads beside it, if any.
- `runs` run in order, each naming its program, so one program can run several times. They pass values to each other **by name**. An input can be a key of the robot's frame (such as `observation.state`), `noise`, a named constant, or an output of an earlier run. The last run outputs `action`.
- For a policy that starts from random noise, on a CUDA device (`executorch_cuda`, `executorch_tensorrt`) the first run takes no inputs and draws `noise` on the GPU, so a chunk copies only the robot's frame there. ExecuTorch 1.6 cannot seed that draw, so it cannot be replayed exactly. Replays and debugging use noise from the host, through the same `noise` input, as the built-in check does.
- The other keys are empty or `null` for a policy like ACT, which predicts each chunk from the current frame alone and takes no task at run time. `history`, `carry` and `first_runs` are for policies that read past frames or keep values between chunks (see [Past frames](#past-frames) and [Values kept between chunks](#values-kept-between-chunks)). `task_tokens` and `action_tokens` name the files that turn a task into vectors and tokens into actions (see [Tasks](#tasks) and [Actions written as tokens](#actions-written-as-tokens)).
- `runtime_imports` are Python modules to import before the programs load, such as the one that adds TensorRT to ExecuTorch.
- `runtime_options` are settings the runtime applies before the programs load, chosen by the backend. Here all the TensorRT engines share one scratch buffer for their activations, since they run one after another. The settings hold for the rest of the process, so a bundle loaded later in the same process runs with them too. Engines that share the buffer take turns on the GPU, even when two bundles run on two threads, because the TensorRT delegate makes each wait for the one before ([pytorch/TensorRT#4739](https://github.com/pytorch/TensorRT/pull/4739), in Torch-TensorRT 2.15). Load such bundles one at a time, since loading one changes an environment variable and the module search path of the process while it runs.
- `action_scale` is the spread of each action in the training data, in robot units. The checks use it.
- `target` is the GPU the programs were built on, when they run only on that kind of GPU, as a TensorRT engine does. A machine whose GPU has another compute capability refuses the bundle, and another GPU model of the same compute capability gets a warning. `runtime_versions` are the versions of the Python modules the programs need to load. Another version of one gets a warning, but one in `exact_runtime_modules` is refused: a TensorRT engine loads only with the TensorRT version that built it.

A version of LeRobot refuses a bundle whose format or keys it does not know, and says whether to upgrade LeRobot or to export again.

### Built-in checks

The export makes a random test frame and records the actions PyTorch computes for it. On a frame where two choices nearly tie, such as two gripper commands, rounding alone can pick either, so a correct program and a wrong one play equally different actions there. So the export first moves the frame's numbers and the noise by one rounding step, 16 times, and takes the next random frame if the actions move by more than the tolerance, up to 8 frames. Then:

- **At export**, the finished bundle replays the test frame in a fresh process, the same way `lerobot-check-bundle` does. If the actions differ too much from PyTorch's, nothing is written.
- **Part by part**, for a recipe that asks for it, each compiled program runs at export on the inputs its part got in PyTorch, and its outputs may differ from the part's by at most 3 times what rounding alone moves them: other attention kernels and matmul settings, the part in float32, and one rounding step of the largest value. A floating point output that none of these moves, such as a copy, may differ by one rounding step; integers must match exactly. A long chain of bfloat16 programs can amplify rounding until correct and broken programs play equally different actions, but one program on its own cannot. The check is for bfloat16 and float16 programs; a float32 program has no wider rerun to measure its rounding against. LingBot-VA's recipe does this in bfloat16 and float16. A part whose outputs move, when it simply runs again, by more than 3 rounding steps of the least precise float type it reads, holds or returns, and by more than 1e-4 of their largest value, such as one that draws random numbers or keeps dropout on, is refused.
- **At load**, `lerobot-check-bundle` replays the test frame again. Before any program loads, a bundle is refused if this machine does not have its GPU or its runtime modules (another version of a module gets a warning, unless it is in `exact_runtime_modules`), if its programs read a value that nothing gives, or if its manifest names a file outside the bundle folder.

The difference is measured in **normalized units**: each action's difference is divided by its `action_scale`. So the same tolerance means the same thing on every robot. The default tolerance is 2e-05 for a policy with float32 (32-bit) weights: the compiled program computes in full float32, as PyTorch does. For one with bfloat16 or float16 (16-bit) weights it is 0.075, because a compiler may sum 16-bit numbers in another order. GR00T keeps its linear layers in bfloat16 unless `--policy.use_bf16=false`, so it uses 0.075 by default even with float32 weights. In bfloat16, a recipe whose policy runs ten denoising steps, such as pi0.5's, uses 0.2: the steps amplify rounding, as measured on pi0.5's test frame. That catches only large errors: a recipe that swapped two cameras would move pi0.5's actions by about 0.03 there, so check a change to a recipe in float32, where the tolerance is 2e-05. Change the tolerance with `--tolerance`.

<Tip>

float32 is the default because it matches PyTorch most closely. A big policy, such as pi0, pi0.5 or GR00T, exports faster and runs faster in bfloat16. Add `--policy.dtype=bfloat16` to `lerobot-export`, and the check then uses the bfloat16 tolerance.

</Tip>

### Big models: bundles with several programs

On an 8 GB board, pi0, pi0.5, GR00T N1.7, SmolVLA, LaWAM and VLA-JEPA do not fit well as one program. So their recipes cut one chunk into a **chain** of small programs. The programs run in the order the manifest lists their runs, pass values to each other by name, and keep those values in GPU memory. pi0.5 starts from random noise and removes it in ten steps, and its chain looks like this:

```
embed                 cameras, state, task          -> the prompt, as vectors
language_model_0..k   a few language model layers   -> what those layers remember about the prompt
step (x10)            that memory, noisy actions    -> less noisy actions
actions               clean actions                 -> actions in robot units
```

The `step` is one program file that runs ten times, each time with a different time value from a `constants.safetensors` file. The file loads once.

Two things let a board with 8 GB build such a policy:

- The recipe loads only the weights of the part it is tracing, then frees them.
- Each program is compiled in a process of its own, and the memory goes back to the system when that process ends.

The pi0, pi0.5 and GR00T recipes read each part's weights from the checkpoint's `model.safetensors`, so they refuse a checkpoint that holds only a PEFT adapter. Merge the adapter into its base policy first, then export the merged folder:

```python
from lerobot.configs.policies import PreTrainedConfig
from lerobot.policies.factory import load_pretrained_policy, make_pre_post_processors

adapter, merged = "path/to/adapter", "path/to/merged"
config = PreTrainedConfig.from_pretrained(adapter)
load_pretrained_policy(config).merge_and_unload().save_pretrained(merged)
for processor in make_pre_post_processors(config, pretrained_path=adapter):
    processor.save_pretrained(merged)
```

The export also compares the chain's actions with the whole policy's own, which needs three times the size of the policy's checkpoint in memory. Both run in PyTorch, so this comparison keeps its own tolerance, 2e-05 in float32 and 0.075 in bfloat16, whatever `--tolerance` says. On a board that does not have that memory, such as an 8 GB board for pi0.5, the export skips that comparison and logs a line saying so. The bundle is then still compared with PyTorch running the same parts, but not with the whole policy.

### Actions written as tokens

pi0-FAST does not compute numbers for its actions. It writes each action chunk as text: `Action: `, then **FAST tokens** (a compressed form of the chunk), then `|`. It writes one token at a time, and each token needs a full pass of its language model. Its recipe makes this chain:

```
prefill (x1)     cameras, state       -> the first token, and the model's memory of the prompt
step (x255)      the tokens so far    -> the next token
(decoding)       the tokens           -> normalized actions, in NumPy
actions          normalized actions   -> actions in robot units
```

A program cannot stop early, so the bundle runs every step up to `max_decoding_steps` (256 by default), and the decoding ignores the tokens after `|`, as the policy does. A chunk therefore takes as long as the longest answer. For a checkpoint whose answers are short, a smaller `--policy.max_decoding_steps` at export makes each chunk faster, and cuts longer answers as the PyTorch policy with that setting would. Turning the tokens back into numbers is not a program: the bundle does it with NumPy and the FAST tokenizer file it carries, which the manifest names under `action_tokens`, so it does not import PyTorch either. pi0-FAST writes the robot's state into its prompt as text, so its bundle runs only the task given at export.

The recipe exports greedy decoding with the KV cache, which is how pi0-FAST decodes by default (`--policy.temperature=0` and `--policy.use_kv_cache=true`), in float32. A checkpoint saved in bfloat16 needs `--policy.dtype=float32`: in bfloat16 the exported steps round differently from the policy and soon pick other tokens. Before it compiles anything, it checks that the chain generates exactly the policy's tokens for two frames, and that the NumPy decoding gives the policy's actions.

The export's test frames are random images. A fine-tuned checkpoint can answer them with text that does not start with `Action:`, and a checkpoint with `validate_action_token_prefix` on (the default) then refuses its own answer, as it would on the robot. Export such a checkpoint with `--policy.validate_action_token_prefix=false`.

### Past frames

Diffusion Policy, Multi-Task DiT and VQ-BeT read past frames, not only the current one. In PyTorch the policy keeps them in queues that fill on every control tick. A compiled program keeps nothing between runs, so the bundle names those frames in its manifest under `history`, with how many to keep. The bundle then keeps them on every tick and passes them to the programs, oldest first. A policy that samples random numbers inside its steps reads them from the bundle's `noise`, so the compiled policy samples like the PyTorch one.

Diffusion Policy and Multi-Task DiT run their encoder once per chunk, and one denoising step many times in a loop, the same way the pi0.5 chain runs its `step`.

### Values kept between chunks

Some policies keep a value from one chunk to the next, such as a planner that starts each plan from where its previous one ended. A compiled program keeps nothing between runs, so such a program takes the value as an input and returns the new one. The bundle names these values in its manifest under `carry`, with their shapes. The bundle passes each one from a chunk to the next, and starts it again from zeros after a reset. The test case of such a bundle holds a few chunks, and the check plays them in order, so it also checks what is passed on.

TD-MPC is such a planner. It plans each chunk by refining a guess over a few rounds, and starts that guess from where its previous plan ended, or from zeros after a reset. Its random numbers come from the bundle's `noise`, like those of the policies above.

Some policies also compute their first chunks after a reset in another way, such as one that builds a cache from its first frames. Their bundle lists the runs of those chunks under `first_runs`, one list per chunk, and later chunks run `runs`. A value that the first chunk writes, in its own type and on its own device, is listed under `carry` without a shape, so it never starts from zeros. The test case of such a bundle plays a few chunks from a reset tick by tick, as a robot would, and holds the action played at each tick, so the check covers every chunk.

### Tasks

A vision-language-action policy reads a task such as "pick up the cube". To read it, the policy first splits the text into **tokens** (word pieces) with its **tokenizer**, and looks up a vector for each token in its **embedding table**. A compiled program cannot run a tokenizer, so a bundle handles the task in one of two ways:

- **Fixed task.** The default recipe stores the task inside the program, and pi0's chain stores it inside its `embed` program. Give it with `--task="pick up the cube"`, or let the export take the first task of `--dataset.repo_id`. The bundle then runs only that task.
- **Any task.** The pi0.5 and GR00T recipes write `task_tokens` into the bundle: the policy's tokenizer file and its embedding table. At run time, the bundle turns any task into vectors without PyTorch. Tasks known at export, such as the dataset's, are stored ready to use. A new task is tokenized once, in a short-lived child process, so the tokenizer's memory does not stay in the robot process. This needs the `tokenizers` package on the robot computer: `pip install "tokenizers>=0.22"`.

For an any-task bundle, the task's prompt must fit in `--max_task_tokens`. The prompt is the task plus a few fixed words the policy adds around it. By default, the budget is a little more than the longest prompt known at export, as far as the policy's prompt has room.

### PyTorch at export and at run time

- The `lerobot-export` command itself never imports PyTorch. The PyTorch work happens in the processes that trace the policy, compile each program and check a part on its own. They give their memory back when they end.
- `lerobot-check-bundle` loads the compiled programs and never imports PyTorch. Of the installed plugins it loads a runtime plugin only when the bundle names a runtime no loaded package has, since a plugin may import PyTorch.

## FP8 with `--quantize=fp8`

A bundle computes in bfloat16 by default. GPUs with 8-bit float units (compute capability 8.9 or higher: Ada, Hopper, Blackwell, Jetson Thor) can run a policy's matrix multiplications in FP8 instead. The bundle is then smaller and faster, and its actions move, by an amount that depends on the policy.

```bash
pip install "nvidia-modelopt>=0.48"
lerobot-export --backend.type=executorch_tensorrt --policy.path=<checkpoint> \
    --quantize=fp8 --tolerance=<largest difference you accept>
```

On a GPU without FP8, or without NVIDIA Model Optimizer, the export stops before it quantizes anything and says which one is missing.

The export quantizes each part right before it traces it, with NVIDIA Model Optimizer's FP8 settings, measuring value ranges on the one frame the export traces with, which has random images, not your data. The vision towers of vision-language models such as pi0.5 and GR00T stay in bfloat16, and so do the inputs of LayerNorm layers and any input that was all zeros while measuring. The log says how many layers each part quantized.

The bundle's test case still compares the bundle with the unquantized policy, which is why `--tolerance` is required: give the largest difference you accept, in normalized action units. Check the result on real frames of your task before you rely on it.

Measured on an H100 with LIBERO checkpoints, one bundle at a time. The difference is between the normalized actions of the FP8 and the bfloat16 bundles, over 16 dataset frames:

| Policy     | Bundle, bfloat16 to FP8 | Per chunk, bfloat16 to FP8 | Difference, mean / max |
| ---------- | ----------------------- | -------------------------- | ---------------------- |
| GR00T N1.7 | 5.3 GiB to 3.3 GiB      | 19.6 ms to 16.5 ms         | 0.045 / 0.080          |
| pi0.5      | 5.9 GiB to 3.8 GiB      | 33.3 ms to 30.5 ms         | 0.37 / 2.0             |

GR00T stays close to its bfloat16 bundle. pi0.5 moves much more, so with this calibration it needs a large `--tolerance` and is not recommended in FP8.

## Run pi0.5 and GR00T on a Jetson Orin Nano

The Jetson Orin Nano has 8 GB of memory, shared by the CPU and the GPU. The pi0.5 and GR00T recipes are made for it: they build one small part at a time. Both fit and run on a Jetson Orin Nano 8 GB, with the numbers below.

### 1. Prepare the board

- Use JetPack 7, NVIDIA's software for Jetson boards. It brings CUDA 13.
- Install LeRobot with the extras of your policy, dataset and robot, such as `lerobot[pi,dataset,feetech]` for pi0.5 on an SO-101 (`groot` in place of `pi` for GR00T), and the `executorch_tensorrt` packages from [Install](#install). Jetson boards are aarch64 (64-bit Arm), and the same command installs the aarch64 builds for CUDA 13.
- Put the CUDA compiler on your `PATH`: `export PATH=/usr/local/cuda/bin:$PATH`.
- Turn on swap. During a TensorRT build, memory the CPU uses can move to swap, but memory given to the GPU cannot.

### 2. Export on the board

Export on the Orin Nano itself, because a TensorRT engine runs only on the GPU model that built it. The first export takes roughly 10 to 15 minutes.

```bash
lerobot-export \
    --policy.path=<user>/<pi05_checkpoint> \
    --policy.dtype=bfloat16 \
    --backend.type=executorch_tensorrt \
    --dataset.repo_id=<user>/<dataset> \
    --task="pick up the cube"
```

For GR00T N1.7, pass a GR00T checkpoint instead. Close other programs while it runs: the export uses most of the board's memory at its peak.

### Results on the Orin Nano

Measured on a Jetson Orin Nano 8 GB with SO-101 checkpoints, on the first export (no TensorRT timing cache yet), and a 120 second run. Memory is the whole board's, above what it used before the command.

|                                               | pi0.5   | GR00T N1.7 |
| --------------------------------------------- | ------- | ---------- |
| Export time                                   | 565 s   | 893 s      |
| Peak memory during export                     | 5.4 GiB | 4.7 GiB    |
| Time per action chunk                         | 449 ms  | 196 ms     |
| Memory while the robot runs                   | 4.7 GiB | 4.3 GiB    |
| Largest action error per frame, mean          | 0.58°   | 0.67°      |
| Same error for PyTorch in bfloat16, for scale | 0.41°   | 0.79°      |

The error is measured against the PyTorch policy in float32, on 50 dataset frames. The bundles stay close to the error that PyTorch itself makes when it runs the policy in bfloat16. These runs used a rollout process that never imported PyTorch. Loading the PyTorch library alone would take about 0.3 GiB more on an Orin Nano.

### Notes for every backend

- The TD-MPC results used a TD-MPC trained on PushT, which reads keypoints rather than a camera image. TD-MPC picks the best of many sampled plans. When two of them score almost the same, another backend's rounding can make the bundle pick the other one. Its actions then differ from PyTorch's by far more than the tolerance, for that chunk and sometimes the next few. Over 40 chunks this happened once or twice with each backend, and PyTorch itself picks differently on CPU and on GPU at the same chunks. If a TD-MPC export fails its check, export it again with another `--seed`.
- EVO1 runs inside its own `torch.autocast`. A checkpoint trained with a frozen vision-language model (EVO1's stage 1, the default) also runs that model in `torch.no_grad()` there, and PyTorch 2.15 then saves the traced program but refuses to load it (`wrap_with_autocast is missing val field`). pytorch/pytorch#202925 fixes this. A stage 2 checkpoint, such as EVO1's LIBERO one, exports with PyTorch 2.15. EVO1 reads the task, so give it with `--task`, or give the dataset with `--dataset.repo_id`.

Other policies have not been tested with `lerobot-export`.

## Troubleshooting

**`outputs/export/... already exists. Pick another --output_dir.`**
The export never overwrites a bundle. Delete the old folder, or pass `--output_dir`.

**`The executorch_tensorrt backend needs PyTorch 2.15 or newer to export, but PyTorch 2.11.0 is installed.`**
This environment has an older PyTorch. Install PyTorch 2.15 in it, with the command the message shows.

**`The executorch_tensorrt backend could not import what it needs (...). If it is not installed: pip install ...`**, or at run time, **`This bundle was exported with torch_tensorrt_executorch_runtime ..., which is not installed.`** or **`This bundle could not import the Python module 'torch_tensorrt_executorch_runtime', which loads its programs (...).`**
The backend's packages are missing on this machine, or one of them fails to load. If they are missing, install them as shown in [Install](#install). If they are installed, the export's message and the run-time message for the module give in parentheses what fails to load, such as a shared library; fix that.

**`This bundle was exported with tensorrt 11.4.0.106, and this machine has 11.3.0.1. Its programs load only with tensorrt 11.4.0.106 ...`**
A TensorRT engine loads only with the TensorRT version that built it. Install the version the message names, or export the policy again on this machine.

**`The exported policy does not reproduce its test case (... > 2e-05). Export it again on this device.`**
The compiled actions differ from PyTorch's by more than the tolerance. With TensorRT, this usually means the bundle was built on another GPU model: export on the board that runs it. Raise `--tolerance` only if you know the difference does not matter for your task.

**`This act checkpoint cannot be exported: ...`**
The default recipe does not fit this policy, and the message says why. Change the setting it names if your policy works without it, or write a recipe for the policy (see below).

## Add a recipe or a backend

### A recipe

A recipe lives beside the policy's configuration, in `src/lerobot/policies/<type>/export_<type>.py`. Its class name is the policy's config class name with `ExportRecipe` in place of `Config`: `PI05Config` gets `PI05ExportRecipe`. `lerobot-export` finds it on its own.

```python
from collections.abc import Iterator

from lerobot.export.recipe import ExportRecipe, Part, TestCase


class MyPolicyExportRecipe(ExportRecipe):
    def parts(self) -> Iterator[Part]:
        # Yield the parts in the order they run. Each one is traced, saved and freed before the next;
        # the parts are compiled afterwards, each in a process of its own.
        yield Part(
            name="model",
            module=MyChunkModule(self.policy, self.preprocessor, self.postprocessor),
            example_inputs=(image, state),
            inputs=["observation.images.front", "observation.state"],
            outputs=["action"],
        )

    def test_case(self) -> TestCase:
        # A frame as the robot sends it, and the actions PyTorch computes for it.
        return TestCase(frame=frame, noise=None, actions=actions, action_scale=action_scale)
```

Two optional methods cover bigger policies:

- `load` (a class method) builds the recipe from the export configuration. Override it to load each part's weights only when that part is traced.
- `plan()` returns a `RunPlan`, which can hold:
  - `runs`: the list of runs (`ProgramRun`, each naming the part it runs as its program), for a part that runs more than once. Record them in `parts()` as you yield the parts, so the two cannot disagree. For a part that runs once per step, such as a denoising step, `repeated_runs` builds its runs and the constants each run reads;
  - `first_runs`: the runs of each of the first chunks after a reset, one list per chunk, for a policy whose first chunks compute in another way;
  - `constants`: named arrays the runs read, such as time values;
  - `task_tokens`: a `TaskTokenData`, for a bundle that runs any task;
  - `action_tokens`: an `ActionTokenData`, for a policy that writes its actions as tokens, which the bundle turns into actions with NumPy;
  - `history`: how many past frames of each frame key the programs take;
  - `carry`: the values the runs pass from one chunk to the next, with their shapes, or no shape for a value the first chunk writes.

`policies/pi05/export_pi05.py`, `policies/groot/export_groot.py` and `policies/smolvla/export_smolvla.py` are full examples of a chain. `policies/diffusion/export_diffusion.py` shows a recipe that reads past frames, `policies/tdmpc/export_tdmpc.py` one that carries a value between chunks, `policies/lingbot_va/export_lingbot_va.py` one whose first chunks run programs of their own, `policies/pi0_fast/export_pi0_fast.py` one that writes its actions as tokens, and `policies/gaussian_actor/export_gaussian_actor.py` a small change to the default recipe.

### A backend

A backend is one config class, registered under its `--backend.type` name. It compiles one part, already traced by `torch.export`, into one program file. An installed package named `lerobot_backend_<name>` adds a backend when imported, the way `lerobot_runtime_<name>` adds a runtime (below). A backend whose programs ExecuTorch loads builds on `ExecuTorchConfig`, which sets the runtime, the file suffix and the PyTorch the compiler needs:

```python
from dataclasses import dataclass
from pathlib import Path

from torch.export import ExportedProgram

from lerobot.export.backends.executorch import EXECUTORCH, ExecuTorchConfig
from lerobot.export.configs import ExportBackendConfig


@ExportBackendConfig.register_subclass("executorch_mychip")
@dataclass
class ExecuTorchMyChipConfig(ExecuTorchConfig):
    device = "cpu"  # where the programs run; the parts are traced and compiled there too
    runtime_imports = ("mychip_executorch",)  # modules that register the chip with the runtime, if any
    runtime_modules = ("executorch", "mychip_executorch")  # modules whose versions the bundle records
    packages = (EXECUTORCH, "mychip-executorch")  # what to install beside LeRobot to export

    def compile(self, program: ExportedProgram, path: Path) -> Path | None:
        from executorch.exir import to_edge_transform_and_lower
        from mychip_executorch import MyChipPartitioner

        edge = to_edge_transform_and_lower(program, partitioner=[MyChipPartitioner()])
        path.write_bytes(edge.to_executorch().buffer)
        return None  # or a data file written beside `path`, such as separate weights
```

A backend whose `device` is `cuda` records the GPU it builds on in the bundle's `target`, since its programs then run only on that kind of GPU. A backend lists in `exact_runtime_modules` the runtime modules its programs load only at the version that built them, as the TensorRT backend lists `tensorrt`. LeRobot's own backends live in `src/lerobot/export/backends/`.

A backend with a new file format, such as ONNX, also needs a **runtime**: a class that loads one program file and runs it on NumPy arrays (see `Program` in `lerobot.bundle.runtime`). An installed package named `lerobot_runtime_<name>` adds it when imported:

```python
from lerobot.bundle.runtime import Runtime, register_runtime

register_runtime("onnxruntime", Runtime(load=OnnxProgram))
```

A bundle imports such packages only when it names a runtime LeRobot does not have. Nothing in LeRobot changes, and a runtime must not import PyTorch. A runtime that takes a bundle's `runtime_options` also passes `configure`, which applies them before the programs load; a runtime without it refuses a bundle that sets some.
